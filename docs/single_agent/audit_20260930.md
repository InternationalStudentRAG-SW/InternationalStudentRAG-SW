# Single agent 비용·지연·정확도 코드 점검

점검일: 2026-09-30. 현재 작업 디렉터리의 수정 중인 코드까지 읽었다. 서비스 코드는 수정하지 않았다. 기존 테스트 50개와 별도 오프라인 재현을 실행했으며, 새로운 유료 API 호출이나 실제 검색 성능 측정은 하지 않았다. 아래 시간·토큰은 저장된 실행 기록이다. 과거 기록은 당시 코드·환경의 결과이며 현재 코드의 새 벤치마크로 취급하지 않는다.

**핵심 판단**

문제는 agent 개수보다, 질문 난도에 비해 무거운 고정 분석 → 검색 → 반복 검증 → 답변 구조에 있다. 검증이 발견한 부족한 내용을 다음 검색이 충분히 활용하지 못하고, 같은 근거를 다시 읽는 작업이 많다. 동시에 검증의 강한 부분은 인용 문자열·ID 검사이고, 실제 주장과 조건의 정확성을 보장하는 부분은 약하다. 따라서 많은 토큰이 곧 높은 정확도로 이어지지 않는다.

**실행 경로부터 구분해야 한다**

- `Backend/app/api/routes/chat.py:10,148`은 `app.core.agent.run_agent_stream`을 호출한다. 현재 웹 API는 `single_agent.pipeline.run_pipeline`에 연결되어 있지 않다.
- single agent는 평가 스크립트에서 실행된다. 웹 화면에서 느끼는 지연과 single agent CLI 평가의 지연을 같은 경로로 해석하면 안 된다.
- single agent는 동기 호출이며 `on_event`로 단계 이벤트만 낸다. 최종 답변은 JSON 전체가 완성된 뒤 반환한다. 현재 API의 캐시·번역·스트리밍이 이 경로에도 적용된다고 가정할 수 없다.
- `README.md`의 BM25 35% / Vector 65%, 후보 15개 설명과 실제 `retriever.py`의 50% / 50%, 채널별 기본 25개가 다르다. 문서보다 실제 실행 설정을 기준으로 판단해야 한다.

**2. P1 — 반복 검증이 같은 문서를 계속 읽는다**

근거: `verifier.py:85–100,193–224,512–536,625–638`.

- 매 라운드 기존 연결 청크 → 이번 검색 청크 → 나머지 풀을 최대 20개까지 본문 전체로 넣는다.
- 재검증 때는 기존 시스템/사용자 프롬프트에 첫 검증 JSON 전체까지 붙인다. 대상 슬롯만 줄었을 뿐 입력 청크는 줄지 않는다.
- `find_uncited_relevant`는 “관련 있지만 인용하지 않은 청크”가 있으면 호출한다. 다른 청크와 같은 사실인지, 단순 번역본인지, 답이 실제로 불완전한지는 판단하지 않는다.
- 긴 파일명이 청크 메모·인용·갈래·재검증 출력에서 반복된다. 무관한 청크도 `chunk_notes`를 생성한다.

개선: 재검증을 ‘중복 인용 누락’이 아닌 ‘답을 바꾸는 사실·조건 누락’에 한정한다. 추가 사실이 있는 청크와 해당 슬롯의 기존 검증 근거만 넣는다. 청크마다 요청 내 짧은 ID(`E1` 등)를 사용하고 서버가 파일명·페이지로 매핑한다. 미해결 슬롯과 관련된 새 근거만 재검증하되, 새 근거에 모순 신호가 있으면 이미 해결한 슬롯도 다시 연다. 토큰 상한과 슬롯별 최소 근거 확보를 함께 적용한다.

**3. P1 — partial을 무조건 원문 확장으로 처리하고, 부족한 내용은 검색어 생성에 전달하지 않는다**

근거: `search_planner.py:50–79,126–150,284–300`, `searcher.py:186–204`, `verifier.py:488–496`.

- `partial`은 항상 `expand_context`. 다른 문서·다른 조항에 있는 정보가 부족해도 신규 검색으로 전환하지 않는다.
- 검색어 프롬프트에는 `slot.missing_detail`, 현재 `value`, 인용 근거 내용이 없다. 이전 검증이 “어떤 승인 주체가 빠졌다”고 알아냈어도 다음 검색은 일반 슬롯 이름에 의존한다.
- 확장 범위는 앵커 ±1청크로 고정된다. 동일 앵커로 재시도하면 같은 청크를 다시 가져온다. 확장 경계나 방문한 범위를 추적하지 않는다.
- 중복 판정은 검색어 문자열에만 적용한다. 확장에서는 검색어가 달라도 실제로 수행하는 작업이 같을 수 있다.
- 신규 청크가 없어도 `pipeline.py:149–152`가 검증을 실행한다. 무진전 판정은 그 검증 뒤 `decide`에서 이뤄진다.

오프라인 재현: `missing_detail`만 서로 다르게 바꿔도 생성 프롬프트가 완전히 같았다. 같은 앵커 두 번 확장은 동일 ID 목록이었다.

개선: 부족한 이유를 `continuation_missing`, `different_section_needed`, `scope_mismatch`, `conflict`, `not_in_known_sources`처럼 행동과 연결해 기록한다. 표·문장 이어짐일 때 확장하고, 다른 정보가 부족하면 검증된 용어와 `missing_detail`을 이용해 새로 검색한다. `(source, anchor, direction, window)` 및 이미 읽은 경계를 기록한다. 새 근거·범위 변화가 없으면 전체 검증을 건너뛰고 다른 행동을 고른다. 문서 부재는 단순 검색 실패만으로 확정하지 않는다.

**4. P1 — 검색에 쓰이지 않는 문구를 만들기 위해 LLM을 호출한다**

근거: `search_planner.py:284–290`, `searcher.py:265–272`.

첫 자동 확장은 무료 규칙 기반이지만, 이후 `expand_context`는 검색어 생성 LLM을 거친다. 정작 실행 시에는 `query_ko`로 검색하지 않고 앵커만 사용한다. “예외 조항”과 “예외 조항 검토”의 문구 차이가 검색 결과를 바꾸지 않는다.

개선: 확장 계획은 서버에서 직접 만든다. 사람이 볼 사유도 템플릿으로 구성한다. LLM 검색어 생성은 새로운 검색 의도가 필요할 때만 수행한다. 이 변경은 의미적으로 불필요한 호출을 없애므로 우선 적용하기 좋다.

**5. P1 — 최종 청크 7개로 줄여도 reranker 작업량은 그대로다**

근거: `config.py:25–27`, `retriever.py:28–35,52–56,79–108`, `searcher.py:97–100`.

- 기본 BM25 25개와 Vector 25개를 RRF로 합친 후 합집합 전체를 BGE에 넣는다. single agent 경로에서는 최대 50개 후보가 될 수 있다.
- `SEARCH_TOP_K=7`은 BGE가 이미 전체 후보를 처리한 뒤의 결과 개수다. 이를 5개로 줄이는 것만으로 BGE 연산이 줄지 않는다.
- 별도의 RRF 후 후보 상한, query-document pair 재사용, reranker 장치·길이·단계별 시간 계측이 없다.
- `searcher`의 최초 import는 전역 retriever를 만들며 전체 DB 읽기, BM25 구성, BGE 로딩을 포함할 수 있다. 38.8초를 BGE 추론만의 시간으로 단정할 수 없다.
- 과거 동일 실행 파일의 후속 신규 검색도 16~23초 수준이어서 최초 로딩만으로 설명하기도 어렵다. 현재 장치가 CPU인지 GPU인지는 이번 점검에서 측정하지 않았다.

개선: 초기화/쿼리 임베딩/BM25/Vector/RRF/BGE 시간을 각각 남긴다. 서비스 시작 시 준비 완료를 구분하고 cold/warm 지연을 별도로 평가한다. RRF 상위 12·20·30개 등 후보 수를 독립 변수로 실험하고 gold 근거 recall을 유지하는 최소값을 선택한다. 필요한 적용 대상·문서·연도를 활용해 후보를 좁히되, 불확실한 조건으로 hard filter하지 않는다. 하드웨어·토큰 길이·batch 조정은 실제 장치 확인 후 한다.

**6. P1 — 검색 품질의 부담을 검증 LLM으로 넘긴다**

근거: `retriever.py:52,75–94`, `searcher.py:97–100,105–133`, `knowledge_base.py:79–100,127–156`.

- BM25 전처리를 지정하지 않는다. 설치된 `langchain_community/retrievers/bm25.py`를 확인하면 기본은 `text.split()`이다. 한국어 조사·활용형, 표의 문장부호, 영문 대소문자에 대한 정규화가 없다.
- single agent는 한국어 검색어만 `retrieve(query)`에 넣는다. 원문+한국어를 함께 쓰는 retriever의 경로는 사용되지 않는다. 다국어 의미 검색은 가능하지만 원문의 어휘 증거는 잃는다.
- 점수는 저장만 하고 최저 관련도 필터는 없다. `min_similarity_score`는 이 경로에서 쓰이지 않는다. 임계값 하나를 임의로 넣는 것은 recall을 해칠 수 있어 교정이 필요하다.
- D1의 실제 첫 순위는 어학당 수업료 원문이 아닌 학부 모집요강이었다. 자동 확장도 이 청크를 기준으로 했다.
- 청킹은 페이지별로 시작하므로 조항 제목·조건·예외가 페이지 경계에서 분리된다. 슬롯 검증과 ±1 확장만으로 조항 전체 범위를 안정적으로 복원하기 어렵다.

개선: BM25에 한국어/영문 정규화 토크나이저를 명시하고 재색인한다. 원문 질문과 재작성 검색어의 역할을 분리한다. `document_family`, `program`, `track`, `effective_date`, `jurisdiction`, `section_id`, `parent_id` 같은 출처 범위를 저장한다. 작은 청크로 찾고 해당 조항/표 단위를 가져오는 구조를 사용한다. 중복 번역본은 provenance를 유지하면서 사실 단위로 묶고, 다른 규정은 묶지 않는다. 검색 결과의 적용 대상과 관련도에 따라 선택적으로 확장한다.

**7. P1 — 확인된 인용이 있다고 내용도 맞는 것은 아니다**

근거: `verifier.py:253–282,316–357`, `answerer.py:150–167,202–210`.

서버는 인용이 청크에 있는지 확인하지만, `value`가 그 인용으로부터 도출되는지는 확인하지 않는다. 오프라인에서 `quote='Tuition is 100 units.'`, `value='Tuition is 999 units.'`를 넣어도 `supported`가 유지됐다. 이는 모델이 실제로 이 오류를 항상 낸다는 뜻이 아니라, 현재 서버 검증이 막지 못하는 종류의 오류를 보여준다.

최종 답변에서는 `[1]`이 유효한 번호면 그 문장의 내용과 근거 관계를 검사하지 않는다. 잘못된 `[99]`는 번호만 지우고 주장 자체는 남긴다. `partial_answer`의 미확인 사항 안내, 조건별 답변의 대상 구분도 프롬프트 지시 중심이다.

저장된 D6 최종 답변은 ‘학기 중 주 20시간’을 대상 구분 없이 제시한다. 저장된 원문 청크 EN p10#c4는 한국어연수 관련 문맥에 이어지는 예외다. 또한 심판은 기관장·법무부 사전 승인 등 gold에 있는 내용을 답변이 빠뜨렸는데도 facts=1.0을 주었다. 따라서 그 점수를 검증 완료로 해석할 수 없다. 이 관찰은 저장된 문서 간 비교이며 현재 법규에 대한 판단이 아니다.

개선: 근거에서 `주장 + 수치/단위 + 적용 대상 + 선행 조건 + 예외 + 출처 span`을 묶어 추출하고 그 묶음으로 답변을 만든다. 수치·날짜 일치는 규칙으로 확인하고, 복잡한 조건·부정·예외의 관계만 선택적으로 의미 검증한다. 매 답변에 대형 judge를 추가하면 비용 문제가 재현되므로 전체 재검증을 기본값으로 삼지 않는다. 잘못된 인용은 문장 수정·보류로 처리하고, 번호만 제거해 근거 없는 주장을 남기지 않는다.

**8. P1 — 이미 supported인 슬롯은 새 모순 근거를 일반 검증에서 다시 보지 않는다**

근거: `verifier.py:80–82,593–618`, `branching.py:168–214`.

`judge_targets`에서 `supported`를 제외한다. 뒤 라운드에서 새로운 문서·개정 규정이 나와도 해당 슬롯은 통상적인 내용 재판정 대상이 아니다. 갈래 규칙이 `applicable_scope`를 다시 낮추는 예외는 있으나, 이미 확인한 금액·기한·규정 자체의 충돌을 일반적으로 처리하지 못한다.

개선: 검증 결과를 어떤 문서 버전·조건·근거 집합에 대한 결과인지 기록한다. 새 근거가 같은 슬롯의 다른 값·시점·대상을 나타낼 때 해당 슬롯만 다시 연다. 단순히 매번 모든 슬롯을 다시 읽게 하는 방법은 비용 때문에 피한다.

**9. P1 — 조기 종료가 사용자가 명시적으로 요구한 항목까지 무시한다**

근거: `checklist_config.py:103–107`, `verifier.py:461–469`.

T1의 `reference_time`, `variation_notes`는 ID만 보고 부수 항목으로 취급한다. 사용자가 연도를 물어 `reference_time.requirement='required'`가 되었어도 핵심 두 칸이 supported면 미해결 목록을 비우고 `answer`를 반환한다. 오프라인으로 재현했다.

개선: `explicitly_requested`와 `answer_critical`을 구분해 저장하고, 사용자 명시 요구·적용 연도·값을 바꾸는 조건은 조기 종료 대상에서 제외한다. 부수 항목을 더 검색하지 않는 것과 완결 답변으로 선언하는 것도 분리한다.

**10. P2 — 슬롯 과다 생성과 처음부터 재시작하는 대화**

근거: `analyzer.py:85–96,239–297`, `pipeline.py:58–65,89–106`, `answer_schema.py:47`.

- 모든 유형의 설명과 사용자 조건 카탈로그를 매번 보낸다. 현재 단순 수업료 질문도 분석 입력 3,568토큰이다.
- 복합 질문에서 여러 유형의 기본 슬롯을 합치고 조건부 슬롯을 모두 활성화한다. 저장된 D8 분석은 16칸이다. 최대 3라운드에서 모두 해결하려 하니 부분 답변에 도달하기 쉽다.
- `PipelineRun.analysis`에는 이어가기용이라는 주석이 있으나 `run_pipeline`은 기존 analysis/pool/budget를 받지 않는다. 매 턴 재분석하고 빈 풀에서 시작한다.
- 질문 기록 10개는 개수 제한만 있고 토큰 제한은 없다. 답변기는 분석의 intent_summary 자체를 받지 않아 “그럼 어디에 내요?” 같은 후속 질문에서 맥락 전달도 제한된다.

개선: 분류·검색어·명시 조건만 짧게 출력하고 슬롯 기본값은 서버가 채운다. 명시 요청과 답을 바꾸는 조건 위주로 활성화한다. 단순 사실과 복잡한 조건/절차를 분리하고, 불확실할 때만 추가 검증한다. 사용자 조건 변화와 문서 버전을 확인하면서 검증된 근거를 세션 안에서 재사용한다. 고정된 ‘2회 호출’ 강제보다는 필요 없는 호출을 하지 않는 정책이 적절하다.

**11. P1 — 평가 지표와 실행 시간의 집계가 정확하지 않다**

근거: `search_schema.py:52–61`, `llm.py:106–109`, `evaluate/check_pipeline.py:58–75`, `evaluate/compare_answers.py:135–153,159–178`.

- `SearchPlanRun`에는 prompt/completion tokens 필드가 없다. 공통 LLM 함수는 필드가 있을 때만 사용량을 기록한다. `summarize`도 plan_runs를 토큰 합계에서 제외한다. 따라서 2회차 이후 검색어 생성 토큰이 빠진다.
- 임베딩, 캐시 적중 입력 토큰, API 내부 재시도도 통합 계측이 없다. 현재 attempts는 실제 HTTP 요청 수와 다르다.
- 현재 비교 코드는 baseline에 검색 시간을 더하도록 되어 있으나, 기존 저장 결과에는 `search_ms`가 없다. 저장 파일과 현재 코드의 계측 버전이 일치한다고 입증할 수 없어 1.4초 대 35.1초 같은 비율을 전체 속도 차이로 인용하면 안 된다.
- `run_single`의 `context_ids = shown or pool_ids`는 답변기에 실제 넣지 않은 풀을 답변 컨텍스트로 셀 수 있다. `pool_recall`과 `answer_context_recall`을 분리해야 한다.
- 심판은 원문 청크 없이 질문·gold 요약·답변만 읽는다. 작은 사실 하나와 복합 조건 여러 개를 같은 ‘fact’ 1개로 세고, 출처 번호 존재는 사실의 충족을 보장하지 않는다.
- 기존 RAGAS 평가 흐름도 `run_pipeline`을 평가하는 경로가 아니다. 과거 retrieval 평가 성적을 현재 agent 성적으로 읽으면 안 된다.

개선: 모든 단계에 동일한 usage/latency schema를 적용한다. 코드 버전, 모델, corpus 버전, 후보 수, 난도, cold/warm, 실패를 함께 저장한다. gold를 수치·대상·조건·예외별 원자 사실로 나누고 사람이 검수한다. 검색 pool / 검증 shown / 채택 refs / 최종 답변의 네 지점에서 recall·오류를 별도로 측정한다. 실사용 질문·다국어·후속 질문·자료 없음·적용 대상 혼동을 포함한 별도 holdout을 둔다.

**12. P2 — 장애 때 재시도가 겹치고 실패 응답에도 API를 부른다**

근거: `single_agent/llm.py:23–26,45–50,62–73`, `pipeline.py:80–95`, `answerer.py:189–205`.

설치된 OpenAI SDK의 `_constants.py`는 기본 재시도 2회, 요청 timeout 600초다. 클라이언트 생성에서 이를 덮어쓰지 않으며, 자체 API 재시도 1회도 있다. 재시도 가능한 장애에서 형식 시도 하나의 호출이 여러 HTTP 요청으로 늘어날 수 있다. 전체 요청 deadline도 없다. 분석 API 실패 뒤 `finish('error')`는 답변 LLM을 다시 호출한다. 과거 credit 부족 실행에서도 이 패턴이 보인다.

개선: timeout과 전체 시간 예산을 명시하고, 재시도 책임을 한 계층에 모은다. 재시도 가능한 일시 장애만 다시 호출한다. error/no_evidence 등 고정 안내는 언어별 템플릿으로 바로 반환한다. 스트리밍을 추가하면 체감 대기는 개선할 수 있지만 실제 검색·검증 시간이 줄어드는 것은 아니므로 별도 지표로 관리한다.

**권장 변경 순서와 검증 기준**

| 순서 | 변경 | 확인할 결과 |
|---|---|---|
| 1 | 사용량 집계와 단계별 검색 시간, 평가 버전 기록 | 실제 병목·비용의 동일 기준 비교 |
| 2 | 확장 문구 LLM 제거, 동일 확장 재실행 차단, missing_detail 전달 | 신규 유효 근거 1개당 비용 감소 |
| 3 | 명시 요구 조기 종료 버그, 조건·주장·인용 정합성 보완 | required 누락·적용 대상 오류 감소 |
| 4 | 재검증 입력 축소, 중복 사실 재검증 제거, 짧은 evidence ID | 정확도 유지 시 입력/출력 토큰 감소 |
| 5 | RRF 후 후보 상한 및 검색 품질/조항 단위 청킹 실험 | 근거 recall 유지 시 BGE 지연 감소 |
| 6 | 단순 질문 빠른 경로, 복잡 질문만 추가 루프, 세션 상태 재사용 | 질문군별 p50/p95, 총 토큰, 오류율 개선 |

한 번에 모두 바꾸지 말고 변경별 제거 실험을 한다. 현재와 같은 단일 에이전트로도 가능하며 다중 에이전트 전환을 우선 처방할 근거는 없다. 감소율은 새 실험 전에는 보장할 수 없다. 특히 후보 축소·재검증 생략은 조건/예외 recall이 유지되는지 함께 확인해야 한다.

Backend에서 다음을 실행했다.

```powershell

& .\.venv\Scripts\python.exe -m pytest --noconftest -p no:cacheprovider tests/test_single_agent.py -q
# 50 passed, 1 warning (Pydantic class Config deprecation)

$env:PYTHONUTF8='1'
```
