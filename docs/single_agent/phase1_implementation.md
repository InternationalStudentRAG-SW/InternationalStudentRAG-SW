# 1차 개선: 계측 → 확장 계획 → 필수 항목 종료 조건

2026-09-30. 이번 범위는 계측 보완과 두 가지 작은 동작 수정이다. 재검색 전략, 검증 입력 축소, 후보 수, 청킹, 답변 의미 검증은 아직 변경하지 않았다.

## 변경

- 분석·검색 계획·검증·답변의 LLM 호출마다 입력/출력/캐시 입력 토큰, 시간, 실패 유형을 기록한다. 검증의 main/recheck를 구분한다.
- 검색 계획 토큰을 총합에 포함한다. 캐시 입력 토큰은 입력 토큰의 부분집합이므로 총합에 다시 더하지 않는다.
- SDK 호출 수와 형식 재시도 횟수를 분리한다. SDK 내부 HTTP 재시도는 계측하지 않는다. 사용량을 받지 못한 호출은 unknown으로 보존한다.
- 기본 검색의 import/초기화, BM25, 임베딩 포함 Vector, RRF, BGE 시간과 후보 개수·장치를 요청별로 기록한다. 임베딩 토큰은 아직 집계하지 않는다.
- 각 검색의 신규/반환 청크 수와 최종 채택 근거 수를 기록한다. 진행 이벤트에서 이전 라운드 신규 청크까지 더하던 집계 오류도 수정했다.
- 평가 결과에 코드 SHA-256, 주요 설정, 라이브러리 버전, 실험 이름을 남긴다. `--corpus-version`이 없으면 문서 버전은 명시적으로 unknown이다.
- 후속 `expand_context` 계획은 서버가 생성한다. 기록용 검색어를 LLM으로 만들지 않는다. 기존 앵커 탐색·확장 창·예산·칸별 상한은 유지한다.
- T1 조기 종료에서 required 슬롯을 제외한다. 분석기가 명시 요구를 required로 승격했으면 연도·변동 조건·추가 정보도 미해결 상태로 보존한다. 예산이 없으면 완결 답변이 아닌 부분 답변으로 간다.

## 오프라인 검증

- 계측만 추가한 시점: 기존 50개 + 계측 4개 = 54개 통과.
- 동작 수정 전 새 회귀 사례: 10개 실패, 부수 조건의 기존 종료 동작 1개 통과. 두 버그가 기존 코드에서 재현됨을 확인했다.
- 동작 수정 후 최종: 66개 통과. Pydantic 기존 deprecation 경고 1개.
- 같은 앵커에서 이전 계획과 새 계획의 이웃 청크 ID·예산 차감이 동일함을 확인했다.
- 2라운드 가짜 파이프라인은 LLM 5회 → 4회, 동일 근거 풀을 유지한다.
- required 슬롯 3종 × 상태 3종의 9개 사례에서 더 검색하거나 부분 답변하도록 검증했다.
- BGE 계측이 후보 50개를 그대로 평가한 뒤 상위 7개를 반환하는지 확인했다. 성능 개선을 가장한 후보 축소는 하지 않았다.

## 실제 실험과 해석

계측만 추가한 기준선은 D1~D9 각 1회, 모든 단계 gpt-4o-mini로 실행했다. 실행 프로세스가 수정 전 모듈을 로드하고 코드 해시를 기록한 뒤 두 동작 수정을 진행했다. 별도 LLM 심판은 호출하지 않는다.

```powershell
& .\.venv\Scripts\python.exe -u -m evaluate.check_pipeline --dev all --model gpt-4o-mini --verify-model gpt-4o-mini --answer-model gpt-4o-mini --label telemetry-baseline
```

기준선의 각 확장 직전 상태를 `evaluate.replay_expansion_plans`로 재생하면, 동일 상태에서 확장 대상·작업을 유지하면서 계획용 호출이 0회가 되는지 확인할 수 있다. 기록된 계획 시간·토큰은 제거 대상 작업의 비용이며, 전체 파이프라인의 인과적 절감률은 아니다.

```powershell
& .\.venv\Scripts\python.exe -m evaluate.replay_expansion_plans evaluate/results/pipeline_BASELINE.json --output evaluate/results/phase1_expansion_replay.json
```

수정 후 실호출은 D1·D6를 대상으로 연결 오류와 잔존 문제를 확인했다. 1회 실행은 생성 변동과 초기화 시간을 통제하지 못하므로 개선율을 확정하는 실험으로 쓰지 않는다.

## 저장된 결과

- 기준선: `Backend/evaluate/results/pipeline_20260930_221219.json` (9문항)
- 고정 상태 재생: `Backend/evaluate/results/phase1_expansion_replay.json` (13개 확장 계획)
- 수정 후 실행: `Backend/evaluate/results/pipeline_20260930_221448.json` (D1·D6)

기준선 총 시간은 644.708초, 총 생성 LLM 토큰은 324,726이다. 그중 검증이 266,432토큰(82.0%) 및 320.102초(49.7%)였다. 기록된 생성 LLM 호출은 모두 usage를 반환했다. 임베딩 토큰은 이 합계에 포함되지 않는다.

새로 확인한 검색 병목: 12회 신규 검색 모두 BGE 장치가 **CPU**였고, 37~47쌍을 재정렬하는 데 호출당 약 **15.3~21.2초**가 걸렸다. 최초 import/초기화는 별도로 12.68초였다. 임베딩 포함 Vector는 약 0.17~2.50초, BM25는 수 ms 이하였다. 이제 CPU BGE 비용을 추정이 아니라 실제 계측으로 확인했다.

고정 상태 재생 13건은 모두 확장 대상·작업을 유지하고 LLM 0회로 계획했다. 기준선에서 이 작업에 사용한 **SDK 호출 13회, 6,917토큰, 계획 시간 합계 15.888초**가 제거 대상이다. 전체 기준선 토큰의 약 2.1%로, 불필요한 작업은 제거했지만 주요 병목은 그대로다.

| 질문 | 기준선 → 수정 후 시간 | 기록 토큰 | SDK 호출 |
|---|---|---|---|
| D1 수업료 | 46.484 → 41.613초 | 9,854 → 9,731 | 3 → 3 |
| D6 GKS 아르바이트 | 75.559 → 72.544초 | 40,571 → 39,220 | 10 → 8 |

D6의 검색 계획 호출·토큰은 수정 후 0이었다. 두 결과 모두 3라운드 부분 답변이다. 전체 시간·토큰 차이는 LLM 판정과 서버 지연 변동도 포함하므로 모두 이번 수정 효과라고 볼 수 없다. 순수 확장 계획 효과는 위의 고정 상태 재생을 기준으로 삼는다.

**잔존 문제도 확인했다.** 수정 후 D1은 여전히 수업료의 ‘학기당’ 단위를 누락했고, D6은 필요한 조건을 충분히 담지 못했다. D6 마지막 확장은 새 청크 0개인데 후속 검증에서 다시 **11.417초·10,292토큰**을 사용했다. 다음 단계의 직접적인 표적은 동일 확장 반복과 무진전 재검증이다. 이번에는 조건별 완결성·최종 정확도를 해결했다고 평가하지 않는다.

문서/색인 버전은 이 실험에서 자동 해시하지 않았고 명시 버전도 전달하지 않아 unknown으로 기록했다. 이 작업 중 문서·색인 업데이트는 수행하지 않았지만, 향후 반복 실험에서는 `--corpus-version`을 지정하고 독립 holdout을 추가해야 한다.

## 남은 작업

1. `missing_detail`을 검색 계획에 전달하고, 다른 조항이 필요한 partial은 신규 검색으로 전환한다.
2. 동일 앵커·범위 재확장을 막는다. 이번 변경은 확장 **계획용 LLM**만 제거했으며 확장 자체의 중복 방지는 아직 아니다.
3. 변화 없는 근거의 전체 재검증을 줄인다. 판정 실패·조건 변화·새 모순은 재검증 예외로 유지한다.
4. 최종 답변의 조건별 갈래·언어·수치/단위 누락 및 적용 대상 혼합을 보완한다.

명시 요구 종료 수정은 분석기의 required 분류가 정확하다는 전제가 있다. 요구 추출 자체의 오류까지 해결한 것은 아니다. 전체 정확도 향상과 큰 지연 감소를 이번 범위만으로 주장하지 않는다.
